# 角色日記管線優化：討論共識與設計推導

## 1. 背景：我們一開始是在查什麼

目前 Character Diary 的實際管線已確認：

* 使用獨立 API 生成日記，模型為 `openai/gpt-5.6-luna`
* 每 `5` 樓觸發一次
* `maxWindowFloors = 40`
* 每個角色會帶最近 `2` 篇舊 Diary
* `worldbookLink = false`
* User message 目前大致是：

  1. 已知角色名單
  2. 各角色已有記憶（最近 Diary）
  3. 本次劇情片段
  4. 輸出 JSON  

我們原本注意到的症狀，是范婼慧的多篇日記裡出現重複或非常相似的心理句，例如：

> 「我好像越來越不像原來的我，但我竟然／可我不討厭這樣。」

最初懷疑「舊 Diary 被回餵 → 下一篇繼續沿用 → 形成自我強化」。

但討論後我們**不把這個當成已證實根因**。

目前至少存在三種可能：

> A. 劇情本身真的正在持續同一條心理發展。
> B. 舊 Diary 對新 Diary 形成 anchoring / 自我回饋。
> C. 模型本身偏好「越來越……」「不像以前……」這種日記式心理發展句型。

因此：

> **「出現重複」不是我們真正要解決的問題，也不能直接把重複當成 bug。**

---

# 2. 第一個重要轉折：目標不是「去重」，而是提升 Diary 品質

我們形成的共識是：

> **只要一篇 Diary 忠於本次劇情、符合角色、心理發展合理，而且舊狀態的延續有依據，那重複本身可以完全不是問題。**

例如角色真的連續幾天都在意同一件事，那日記反覆碰到同一心理核心是自然的。

真正需要判斷的是：

> **「這次為什麼又寫這個心理結論？」**

如果原因是：

> 本批新劇情又提供了新的相關經驗，

那是正常 continuity。

如果原因只是：

> 上一篇 Diary 已經這樣寫，所以這篇順著再寫一次，

才是機制性污染。

因此我們不把：

> repetition rate / 重複率下降

當主要成功指標。

優先評估的是：

* 是否忠於本次劇情
* 是否符合角色
* 是否與近期心理狀態連續
* 新心理判斷是否有本次劇情支撐
* 沒有新變化時，是否能自然維持原狀，而不是硬製造成長

---

# 3. 第二個轉折：不要硬要求模型「每篇都要有變化」

曾討論過是否新增：

> `new_change` / 本批心理變化

之類的欄位。

最後傾向**不這麼做**。

原因是：

> 一旦 schema 強迫每篇都要輸出「變化」，模型很可能在沒有真正變化時也製造一個變化。

這會造成比重複更糟的結果：

> 每五樓角色就自動「更依賴 → 更害怕失去 → 更願意承諾 → 更成熟……」

像心理狀態自動升級。

所以目前原則是：

> **Diary 負責記錄這次經歷對角色的感受與理解，不負責強制偵測人格變化。**

跨多篇 Diary 的長期變化，應該由未來獨立的 Learned Self / reflection 層處理。

---

# 4. 第三個轉折：我們發現真正問題是「資訊沒有明確身分」

討論 40 輪視窗時，一開始很容易掉進：

> 40 太多嗎？
> 要不要改 20？
> 改 10？
> 改 5？

但後來我們重新定義問題：

> **本質不是 context 太長，而是 context 裡不同性質的資訊被平坦地丟給模型。**

在模型眼中，目前可能同時存在：

> 舊劇情
> 新劇情
> 舊 Diary
> 未來可能加入的角色原始設定

但系統沒有非常清楚地告訴它：

> 哪些是什麼資訊，以及它們各自應該怎麼用。

因此形成一個更底層的設計原則：

> **資訊處理之前，要先定義資訊。**

也可以說：

> **先分類，再處理。**

---

# 5. 對 40 輪的重新理解

40 輪當初存在有合理的遊戲需求：

> RP 中一個事件可能持續很多輪。
> 一場吵架、約會、談心甚至可能跑 20～30 輪。
> 如果 Diary 每次只看最近 5 輪，很容易只看到事件尾巴。

所以：

> **我們不認為「40」本身是錯的。**

真正粗暴的是：

> **把最近 40 輪全部當成同一種、本篇都應重新消化的資訊。**

我們現在比較傾向把它重新定義為：

> **40 輪 = Recent Raw Buffer / 近期原始劇情池**

也就是：

> 系統最多保留最近 40 輪供 Diary 建立上下文，

而不是：

> 每次生成 Diary，都把這 40 輪全部當成本次新事件。

白話說：

> **40 輪是倉庫，不是購物清單。**

---

# 6. 新的資訊分層

目前討論出的理想語義結構是：

### A. Character Baseline

回答：

> 她原本大致是什麼樣的人？

例如：

* 自我理解
* 核心價值
* 人際／親密關係傾向
* 面對衝突與不確定性的慣常方式
* 重要邊界
* 表達風格

Baseline 未來應由角色卡自動歸納成固定內部 schema。

重要原則：

> schema 可以固定，但角色卡沒寫的資訊不能硬冒充設定。

可區分：

* explicit：角色卡明確設定
* inferred：合理推論
* unknown：資料不足

Baseline 是後續方向，但**不是這一輪 V1 必須一起完成的前置條件**。

---

### B. Recent Psychological Context

即最近 1～2 篇舊 Diary。

它的職責是：

> **讓模型知道角色最近心理走到哪裡。**

它不是：

> 本篇新的事件證據。

因此舊 Diary 不是要刪除或弱化到沒有作用，而是：

> **縮窄它的職責。**

一句話：

> **舊 Diary 負責 continuity，不負責 new evidence。**

---

### C. Previous Story Context / 前情語境

這是已經發生過、可能上一篇 Diary 也處理過的劇情。

它存在只是因為：

> 本次新劇情可能從一句對話中間開始，如果完全切斷前文，模型會看不懂。

例如：

```text
【前情語境｜已處理，只供理解】
#748 ...
#749 ...
#750 宇璽：「那如果下船之後……」
```

它可以被模型閱讀，但：

> **不能因為再次出現在 prompt 裡，就重新變成本篇的新事件證據。**

---

### D. Current New Experience / 本次新增經歷

這才是：

> **上一篇 Diary 成功處理之後，新發生而尚未被 Diary 消化的劇情。**

例如：

```text
【本次新增經歷｜本篇日記主要依據】
#751 ...
#752 ...
...
#755 ...
```

這是本篇 Diary 最主要應處理的資料。

一句話：

> **新劇情負責 evidence。**

---

# 7. Checkpoint：V1 最重要的機械狀態

為了讓系統不用靠 LLM 猜哪些是新劇情，需要新增／確認一個明確 checkpoint：

> `last_diary_processed_turn`

概念：

> **記錄這個角色／聊天的上一篇成功 Diary 已經處理到哪一樓。**

例如：

```text
last_diary_processed_turn = 795
current_turn = 800
```

則：

> `<=795` = 已處理過的內容
> `796–800` = 尚未處理的新經歷

如果 800 那次 API 生成失敗：

> checkpoint 不更新，仍然是 795。

劇情跑到 805 後再次觸發：

> `796–805` 都仍然屬於尚未處理的新內容。

直到生成成功，才：

```text
last_diary_processed_turn = 805
```

因此 checkpoint 同時防止：

### 漏處理

API 某次失敗，不會讓中間劇情永久消失。

### 重複當新內容

已經處理過的劇情即使還存在於最近 40 輪 buffer，也不會被重新標成新經歷。

核心原則：

> **能用機械狀態確定的資訊身分，不要交給模型猜。**

---

# 8. Trigger 和 Reading Window 必須分開

這也是討論中形成的重要區別：

> **每 5 樓觸發 Diary ≠ 每篇 Diary 只能讀 5 樓。**

`interval = 5` 只代表：

> 「什麼時候嘗試產生日記。」

真正的讀取範圍應該由：

> **上一篇成功處理到哪裡**

決定。

因此：

```text
Trigger = cadence
Checkpoint = progress
40-floor buffer = available context
```

三者不應混成同一個概念。

---

# 9. 為什麼仍然需要少量 overlap / 前情

完全按照 checkpoint 硬切也會有問題。

例如：

```text
#750 宇璽：「那如果下船以後……」
```

上一篇處理到 750。

而：

```text
#751 范婼慧：「你怎麼突然問這個？」
```

才是新內容。

如果 Diary 只看到 751 以後，它可能不知道角色到底在回答什麼。

因此：

> **新舊邊界必須明確，但允許帶少量已處理劇情作為前情。**

第一版不需要做 AI event detection。

可以先使用：

> 固定少量 overlap / 前情

並明確標示：

> 這些資料只幫助理解，不是本篇新事件。

如果未來實測發現固定 overlap 經常切不到真正事件起點，再考慮第二階段：

> Event-based context selection / 事件式前情選取。

---

# 10. 為什麼不立刻做智慧事件切分

我們討論過，人類確實會依「事件」理解經驗，而不是每 5 句話切一次。

長期來看：

> Diary 讀取「事件」可能比固定樓數更自然。

但現階段不建議立刻加入：

> 讓另一個 LLM 判斷事件從哪裡開始。

理由：

現在真正需要驗證的是：

> **只要把資訊身分標清楚，Diary 品質是否已經改善？**

如果同時加入事件偵測模型：

> prompt 改了
> reading window 改了
> event detection 又加入了

那結果變好／變壞時，很難知道是哪一層造成。

所以我們決定：

> **先做最小可驗證改動，再決定是否增加智慧。**

---

# 11. V1 行動方向

目前最適合實作與驗證的第一版：

### 保持不變

* `interval = 5`
* `maxWindowFloors = 40`
* Diary 生成模型
* temperature
* 目前 Diary schema
* 最近 Diary 數量先維持 1～2 篇
* 暫不加入 vector retrieval
* 暫不加入 AI event segmentation
* 暫不強迫輸出「心理變化」

### 新增／調整

**1. 明確 checkpoint**

```text
last_diary_processed_turn
```

只有 Diary 成功完成後才更新。

**2. 把近期 40 輪重新定義成 buffer，而非全部 new story。**

**3. 組裝 prompt 時，至少分成：**

```text
【近期心理背景｜歷史參考】
最近 Diary

【前情語境｜已處理，只供理解】
少量 checkpoint 前內容

【本次新增經歷｜本篇主要依據】
checkpoint 後尚未處理的劇情
```

未來 Character Baseline 完成後，再增加：

```text
【角色基線｜角色原始穩定特質】
...
```

**4. Prompt 要明確告訴模型各資料角色。**

核心語意不是「禁止重複」，而是：

> 近期心理背景與前情語境用於理解角色和事件連續性。
> 本篇主要消化「本次新增經歷」。
> 若本次沒有產生新的心理發展，可以自然延續既有狀態，不必刻意製造變化。

---

# 12. V1 不應該做什麼

這點請編程 Agent 特別注意。

目前**不要因為想解重複問題而**：

* 刪掉舊 Diary
* 把 40 直接改成 5
* 強制每篇輸出 `new_change`
* 加一堆去重規則
* 用 regex 禁止「越來越」
* 直接做 embedding retrieval
* 直接做 AI event detection
* 把 Learned Self 判斷塞回 Diary
* 因為某些重複句而改變整個 Diary schema

因為我們現在的問題定義不是：

> 「如何讓句子不重複。」

而是：

> **「如何讓模型正確知道不同輸入資訊的身分與職責，從而產生高品質的角色日記。」**

---

# 13. V1 驗證重點

修改後不要只計算重複率。

優先人工觀察：

> 1. Diary 是否更集中於 checkpoint 後真正的新經歷？
> 2. 是否仍能理解需要前情才能看懂的事件？
> 3. 舊 Diary 是否仍提供合理心理連續性？
> 4. 是否減少「沒有新劇情支撐卻持續放大舊心理結論」？
> 5. 沒有心理變化時，Diary 是否能自然記錄當下，而不是硬製造成長？
> 6. API 失敗後，checkpoint 是否能確保未處理內容下一次被補上？

重複句可以作為觀察項，但：

> **不是主要 KPI。**

# 14. 整個推導可以濃縮成這條路徑

```text
發現多篇 Diary 重複心理句
        ↓
先懷疑舊 Diary 回饋污染
        ↓
發現不能排除真實劇情延續與模型文體習慣
        ↓
因此「去重」不是正確問題定義
        ↓
重新定義目標：
Diary 品質、角色一致性、對本次經歷的忠實理解
        ↓
發現現有輸入把舊 Diary、近期劇情等資料較平坦地交給模型
        ↓
得到更底層原則：
資訊處理之前，先定義資訊身分
        ↓
重新理解 40 輪：
不是本篇內容，而是近期原始資料池
        ↓
區分：
角色基線 / 近期心理背景 / 前情語境 / 本次新增經歷
        ↓
需要一個機械 checkpoint
知道「上一次成功處理到哪裡」
        ↓
V1：
不動 40、不動 5 樓觸發、不增加複雜模型
先加入 checkpoint + 資訊分層 + 少量前情
        ↓
觀察 Diary 品質
        ↓
只有證據顯示仍不足，
才進一步做前情縮減、相關性檢索或事件式切分
```

最後一句可以直接給 Agent 當設計意圖：

> **這次修改不是為了「減少 Diary 重複」，而是為了讓 Diary generation 擁有有明確時間邊界與證據角色的 context：系統機械知道哪些劇情已處理、哪些尚未處理；舊 Diary 與前情只提供 continuity/context，本次新增劇情才是本篇主要 evidence。先以最小改動驗證這個資訊分層是否能提升 Diary 品質，再決定是否需要更複雜的事件切分或 retrieval。**
